Decision Guide: When to Use What

Scenario Solution Why
Simple async in one component useEffect + useState No need for global state — keep it local
Async data needed in Redux store createAsyncThunk + extraReducers Multiple consumers, complex state logic, non-CRUD operations
Multiple CRUD endpoints, caching, auto-refetch RTK Query Minimal boilerplate, automatic cache management, tag-based invalidation

Quick Reference: createAsyncThunk API

Concept Description
createAsyncThunk(typePrefix, payloadCreator) Creates a thunk that dispatches pending/fulfilled/rejected actions
thunkAPI.rejectWithValue(value) Return structured error data in the rejected action's payload
thunkAPI.getState() Access current Redux state inside the thunk
thunkAPI.dispatch(action) Dispatch other actions from within the thunk
extraReducers: (builder) => {} Handle thunk lifecycle actions in a slice
.addCase(thunk.pending, reducer) Handle the loading state
.addCase(thunk.fulfilled, reducer) Handle successful response
.addCase(thunk.rejected, reducer) Handle error state

Quick Reference: RTK Query API

Concept Description
createApi({ ... }) Define your API — endpoints, base URL, tags
fetchBaseQuery({ baseUrl }) Lightweight fetch wrapper with JSON handling
builder.query<Result, Arg> Define a GET endpoint (reading data)
builder.mutation<Result, Arg> Define a POST/PUT/DELETE endpoint (changing data)
providesTags Declare what cache tags a query provides
invalidatesTags Declare what cache tags a mutation invalidates
useXxxQuery(arg, options?) Auto-generated hook for queries
useXxxMutation() Auto-generated hook for mutations — returns [trigger, result]
skip Option to conditionally skip a query
pollingInterval Option to refetch at a regular interval (ms)

Common Patterns

Optimistic Updates — update the cache immediately before the server responds:

addPost: builder.mutation<Post, Omit<Post, "id">>({
  query: (newPost) => ({
    url: "/posts",
    method: "POST",
    body: newPost,
  }),
  async onQueryStarted(newPost, { dispatch, queryFulfilled }) {
    // Optimistically add to cache
    const patchResult = dispatch(
      postsApi.util.updateQueryData("getPosts", undefined, (draft) => {
        draft.push({ ...newPost, id: "temp-id" });
      })
    );
    try {
      await queryFulfilled;
    } catch {
      // Revert on failure
      patchResult.undo();
    }
  },
})

Conditional Fetching — only fetch when a condition is met:

const { data } = useGetUserProfileQuery(userId, {
  skip: !userId, // Don't fetch until we have a userId
});

Polling — keep data fresh with automatic refetching:

const { data: notifications } = useGetNotificationsQuery(undefined, {
  pollingInterval: 10000, // Refetch every 10 seconds
});

Typical File Structure with RTK Query

store/
  store.ts          // configureStore — combines reducers + API middleware
  hooks.ts          // useAppDispatch, useAppSelector
  slices/
    userSlice.ts    // createSlice for non-API state (UI state, auth, etc.)
    cartSlice.ts
  api/
    postsApi.ts     // createApi for posts endpoints
    usersApi.ts     // createApi for users endpoints
    baseQuery.ts    // shared fetchBaseQuery config (optional)

Key Takeaways

  • createAsyncThunk — use when you need full control over async logic in Redux, or for non-CRUD operations (WebSocket messages, complex multi-step flows)
  • RTK Query — use for standard API interactions (CRUD). It eliminates boilerplate and gives you caching, invalidation, and auto-generated hooks for free
  • Both tools are part of @reduxjs/toolkit — no extra packages needed
  • You can use both in the same app: RTK Query for data fetching, createAsyncThunk for complex async logic that doesn't fit the query/mutation model
