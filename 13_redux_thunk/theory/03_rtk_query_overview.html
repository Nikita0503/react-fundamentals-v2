What is RTK Query?

RTK Query is a data fetching and caching tool built directly into Redux Toolkit. It's designed to simplify the most common data-fetching patterns in Redux apps.

Think of it as Redux's answer to React Query / TanStack Query — but integrated into the Redux store.

Why Does It Exist?

The createAsyncThunk + extraReducers approach works, but it requires a lot of boilerplate for every single endpoint:

  • Define the thunk
  • Define the state shape (data, status, error)
  • Handle 3 lifecycle actions in extraReducers
  • Manually manage cache invalidation
  • Manually handle refetching
  • Repeat for every API endpoint...

RTK Query eliminates all of this repetition.

What RTK Query Handles Automatically

  • Caching — responses are cached and reused
  • Deduplication — multiple components requesting the same data = one network request
  • Polling — automatic refetching at intervals
  • Cache invalidation — tag-based system to refetch stale data
  • Loading states — isLoading, isFetching, isSuccess, isError
  • Error states — structured error handling
  • Refetch on focus/reconnect — configurable automatic refetching

Core Concepts

createApi — the single function where you define your entire API. All endpoints, their types, and their cache behavior live here.

fetchBaseQuery — a lightweight wrapper around the native fetch API. Think of it like a simpler axios — it handles JSON serialization, base URLs, and headers.

Basic Setup

// store/api/postsApi.ts
import { createApi, fetchBaseQuery } from "@reduxjs/toolkit/query/react";

type Post = {
  id: string;
  title: string;
  body: string;
  authorId: string;
};

export const postsApi = createApi({
  // Unique key for this API's cache in the Redux store
  reducerPath: "postsApi",

  // Base configuration for all requests (base URL, headers, etc.)
  baseQuery: fetchBaseQuery({ baseUrl: "/api" }),

  // Tag types used for cache invalidation (we'll explain below)
  tagTypes: ["Post"],

  // All API endpoints defined here
  endpoints: (builder) => ({

    // GET /api/posts — returns Post[], takes no argument (void)
    getPosts: builder.query<Post[], void>({
      query: () => "/posts",
      providesTags: ["Post"], // this data is tagged as "Post"
    }),

    // GET /api/posts/:id — returns Post, takes postId as argument
    getPostById: builder.query<Post, string>({
      query: (postId) => `/posts/${postId}`,
    }),

    // POST /api/posts — takes a new post object (without id), returns the created Post
    addPost: builder.mutation<Post, Omit<Post, "id">>({
      query: (newPost) => ({
        url: "/posts",
        method: "POST",
        body: newPost,
      }),
      invalidatesTags: ["Post"], // after adding, refetch all "Post" queries
    }),

    // DELETE /api/posts/:id — takes postId (string), returns nothing (void)
    deletePost: builder.mutation<void, string>({
      query: (postId) => ({
        url: `/posts/${postId}`,
        method: "DELETE",
      }),
      invalidatesTags: ["Post"], // after deleting, refetch all "Post" queries
    }),
  }),
});

// RTK Query auto-generates a hook for each endpoint!
// Naming: "use" + endpoint name + "Query" (for queries) or "Mutation" (for mutations)
export const {
  useGetPostsQuery,
  useGetPostByIdQuery,
  useAddPostMutation,
  useDeletePostMutation,
} = postsApi;

Key parts explained:

  • reducerPath — a unique name for this API's slice in the Redux store (like a namespace)
  • baseQuery — the base URL all endpoints will use. fetchBaseQuery is a thin wrapper around fetch
  • tagTypes — labels used for cache invalidation (when data changes, which cached queries should refetch?)
  • builder.query<ReturnType, ArgType> — defines a GET endpoint. First generic = what it returns, second = what argument it takes
  • builder.mutation<ReturnType, ArgType> — defines a POST/PUT/DELETE endpoint
  • providesTags — "this query provides data tagged as Post" (used for cache tracking)
  • invalidatesTags — "after this mutation, refetch all queries tagged as Post" (automatic cache refresh)

Adding to the Store

RTK Query creates its own reducer and middleware. You add them to your store:

// store/store.ts
import { configureStore } from "@reduxjs/toolkit";
import { postsApi } from "./api/postsApi";
import { userReducer } from "./slices/userSlice";

export const store = configureStore({
  reducer: {
    user: userReducer,
    [postsApi.reducerPath]: postsApi.reducer,
  },
  middleware: (getDefaultMiddleware) =>
    getDefaultMiddleware().concat(postsApi.middleware),
});

export type RootState = ReturnType<typeof store.getState>;
export type AppDispatch = typeof store.dispatch;

Comparison: createAsyncThunk vs RTK Query

Aspect createAsyncThunk approach RTK Query approach
Files needed per endpoint Thunk file + slice (extraReducers) + state type Just add an endpoint to createApi
Loading/error state Manual — define status, error in state Automatic — isLoading, isError, etc.
Caching Manual — you manage it yourself Automatic — tag-based invalidation
Deduplication Not built-in Automatic — same query = one request
Refetching Manual dispatch Automatic on focus, reconnect, or interval
Boilerplate per endpoint ~40-60 lines ~5-10 lines
Best for Complex async logic, non-CRUD operations Standard CRUD APIs, data fetching

Endpoint Types

RTK Query has two types of endpoints:

  • builder.query — for reading data (GET requests). Generates a useXxxQuery hook.
  • builder.mutation — for changing data (POST, PUT, DELETE). Generates a useXxxMutation hook.
endpoints: (builder) => ({
  // Query — reading data (GET)
  getUsers: builder.query<User[], void>({
    query: () => "/users",
  }),

  // Mutation — changing data (POST/PUT/DELETE)
  updateUser: builder.mutation<User, { id: string; name: string }>({
    query: ({ id, ...body }) => ({
      url: `/users/${id}`,
      method: "PUT",
      body,
    }),
  }),
})
