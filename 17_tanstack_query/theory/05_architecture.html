The Modern React Data Architecture

  • Client state (UI state, user preferences, filters) → Zustand
  • Server state (API data, cached responses) → TanStack Query
  • They don't overlap — each handles what it's best at

Example: Zustand + TanStack Query Working Together

// stores/useFilterStore.ts — client state (Zustand)
import { create } from "zustand";

type FilterStore = {
  category: string;
  sortBy: "date" | "price";
  setCategory: (category: string) => void;
  setSortBy: (sort: "date" | "price") => void;
};

export const useFilterStore = create<FilterStore>((set) => ({
  category: "all",
  sortBy: "date",
  setCategory: (category) => set({ category }),
  setSortBy: (sortBy) => set({ sortBy }),
}));
// hooks/useProducts.ts — server state (TanStack Query)
import { useQuery } from "@tanstack/react-query";
import { useFilterStore } from "../stores/useFilterStore";

export const useProducts = () => {
  const category = useFilterStore((s) => s.category);
  const sortBy = useFilterStore((s) => s.sortBy);

  return useQuery<Product[]>({
    // queryKey includes the filters — when category or sortBy changes,
    // TanStack Query treats it as a NEW query and fetches fresh data automatically
    queryKey: ["products", { category, sortBy }],
    queryFn: () => fetch(`/api/products?category=${category}&sort=${sortBy}`).then(r => r.json()),
  });
};
// components/ProductPage.tsx — uses both
const ProductPage = () => {
  const { category, setCategory, sortBy, setSortBy } = useFilterStore();
  const { data: products, isLoading } = useProducts();

  return (
    <div>
      <select value={category} onChange={e => setCategory(e.target.value)}>...</select>
      <select value={sortBy} onChange={e => setSortBy(e.target.value as "date" | "price")}>...</select>
      {isLoading ? <p>Loading...</p> : <ProductList products={products ?? []} />}
    </div>
  );
};

Filter changes → queryKey changes → TanStack Query auto-fetches new data → UI updates. No manual useEffect, no manual loading state, no manual cache management.

Custom Query Hooks — Abstract API Details

// hooks/queries/usePosts.ts
export const usePosts = () => useQuery<Post[]>({
  queryKey: ["posts"],
  queryFn: () => httpClient.get("/posts").then(r => r.data),
});

// hooks/queries/usePost.ts
export const usePost = (id: number) => useQuery<Post>({
  queryKey: ["posts", id],
  queryFn: () => httpClient.get(`/posts/${id}`).then(r => r.data),
  enabled: !!id,
});

// hooks/mutations/useCreatePost.ts
export const useCreatePost = () => {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: (data: CreatePostDto) => httpClient.post("/posts", data),
    onSuccess: () => queryClient.invalidateQueries({ queryKey: ["posts"] }),
  });
};

RTK Query vs TanStack Query — When to Choose Which

CriteriaRTK QueryTanStack Query
DependencyPart of @reduxjs/toolkitStandalone package
Client state pairingRedux (same store)Any (Zustand, Context, etc.)
Infinite scrollManual implementationuseInfiniteQuery built-in
Cache invalidationTag-based (declarative)queryKey-based (imperative)
Code generation (OpenAPI)Official codegenCommunity plugins
DevToolsRedux DevToolsReact Query DevTools
Bundle sizeLarger (entire RTK)Smaller (~13KB)
Learning curveHigher (need Redux knowledge)Lower (standalone)
  • Use RTK Query when: project already uses Redux Toolkit, team standardized on Redux, need OpenAPI codegen
  • Use TanStack Query when: no Redux in project, want lighter setup, need infinite scroll, pairing with Zustand
