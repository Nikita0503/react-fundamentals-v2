The Problem

A typical "correct" fetch implementation with useState + useEffect:

const PostList = () => {
  const [posts, setPosts] = useState<Post[]>([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    const controller = new AbortController();
    setLoading(true);
    fetch("/api/posts", { signal: controller.signal })
      .then(res => res.json())
      .then(data => { setPosts(data); setLoading(false); })
      .catch(err => { if (err.name !== "AbortError") setError(err.message); setLoading(false); });
    return () => controller.abort();
  }, []);

  // What about: caching? refetching on focus? retry on error? stale data? deduplication?
  // You'd need 50+ more lines...
};

This is 15 lines and it doesn't handle many real-world challenges. Let's understand what those challenges are:

The Challenges of Server State

  • Loading state — the user needs feedback while data is being fetched. Without it, the UI feels broken or frozen.
  • Error handling — network requests can fail (server down, no internet, timeout). You need to catch errors and show meaningful messages.
  • Caching — if the user navigates away and comes back, should you fetch again? Or show the data you already have? Caching stores previously fetched data so you don't make redundant requests.
  • Stale data — cached data can become outdated. If another user edited a post, your cached version is "stale" (old). You need a strategy: when to show cached data and when to refetch fresh data.
  • Refetching — when should data be refreshed? On page focus? On interval? After a mutation? Manual trigger? Each scenario needs different logic.
  • Race conditions — if the user changes a filter quickly (A → B → C), three requests fire. Response for B might arrive after C, overwriting newer data with older data. You need to cancel or ignore outdated responses.
  • Deduplication — if 10 components on the same page need the same user data, you don't want 10 separate API calls. One request should serve all of them.
  • Retry — if a request fails due to a temporary network issue, should you retry automatically? How many times? With what delay?

Implementing all of this manually for every API call would require hundreds of lines of boilerplate. TanStack Query handles all of these out of the box.

Server State vs Client State

Different problems need different tools:

Client StateServer State
ExamplesTheme, filters, modal open/closed, form inputUser profile, posts list, product data

What TanStack Query Gives You for Free

  • Automatic caching — same query = same cached data
  • Background refetching — data stays fresh
  • Deduplication — 10 components request same data = 1 network call
  • Stale-while-revalidate — show cached data immediately, refetch in background
  • Automatic retry on failure
  • Window focus refetching
  • Pagination and infinite scroll support
  • Optimistic updates
  • DevTools

Installation and Setup

npm install @tanstack/react-query
npm install @tanstack/react-query-devtools  # optional, for development
// main.tsx
import { QueryClient, QueryClientProvider } from "@tanstack/react-query";
import { ReactQueryDevtools } from "@tanstack/react-query-devtools";

const queryClient = new QueryClient();

const App = () => (
  <QueryClientProvider client={queryClient}>
    <YourApp />
    <ReactQueryDevtools initialIsOpen={false} />
  </QueryClientProvider>
);
  • QueryClient — the cache manager (one per app)
  • QueryClientProvider — makes the client available to all components
  • ReactQueryDevtools — visual tool to inspect cache, queries, mutations (dev only)
