Understanding Re-renders

Understanding re-renders is the foundation of optimization. You can't optimize what you don't understand.

A re-render means React calls your component function again to get the new JSX. This is how React keeps the UI in sync with state.

What Triggers a Re-render

There are exactly three triggers:

  1. State change — when setState is called, the component re-renders
  2. Parent re-renders — when a parent re-renders, ALL its children re-render too (even if their props didn't change!)
  3. Context change — when a context value changes, all consumers re-render

Re-render ≠ DOM Update

This is a critical distinction. React re-renders (runs the component function), diffs the Virtual DOM, and only updates the real DOM if something actually changed. Re-renders are usually fast — it's unnecessary DOM updates that are expensive.

The Re-render Cascade

When a parent's state changes, the entire subtree re-renders:

// When App's state changes, ALL of these re-render:
const App = () => {
  const [count, setCount] = useState(0);
  return (
    <div>
      <Header />          {/* re-renders (parent re-rendered) */}
      <Counter count={count} /> {/* re-renders (parent + props changed) */}
      <Footer />          {/* re-renders (parent re-rendered) — even though nothing changed for it! */}
    </div>
  );
};

This is Usually Fine!

React is fast. Most re-renders are cheap. The problem only arises when:

  • A component is expensive to render (complex calculations, large lists)
  • Re-renders happen very frequently (typing, scrolling, animations)
  • The component tree is very deep

Don't Optimize Prematurely

The golden rule: first make it work correctly, then measure, then optimize only what's slow. Most performance problems are imaginary — React handles the vast majority of cases without any manual optimization.
