The Problem: Props Drilling

As you learned earlier, data flows down through props — from parent to child. But what happens when a deeply nested component needs data from a component far above it in the tree?

You end up passing props through many intermediate components that don't use the data themselves — they just forward it. This is called props drilling, and it makes code harder to maintain:

// App → Layout → Sidebar → UserMenu → Avatar
// Avatar needs the user object, but Layout, Sidebar, and UserMenu don't care about it.
// Yet they all must accept and pass the "user" prop.

type User = { name: string; avatarUrl: string };

const App = () => {
  const [user, setUser] = useState<User>({ name: "Alice", avatarUrl: "/alice.png" });
  return <Layout user={user} />;  // passes user down
};

const Layout = ({ user }: { user: User }) => {
  return <Sidebar user={user} />;  // just forwarding...
};

const Sidebar = ({ user }: { user: User }) => {
  return <UserMenu user={user} />;  // just forwarding...
};

const UserMenu = ({ user }: { user: User }) => { // finally uses user!
  return (
    <div>
      <span>{user.name}</span>
      <Avatar user={user} />
    </div>
  );
};

const Avatar = ({ user }: { user: User }) => { // finally uses user!
  return <img src={user.avatarUrl} alt={user.name} />;
};

The Solution: React Context

React Context lets you share data with any component in the tree without passing props through every intermediate level. It creates a "broadcast channel" — any component can tune in and read the value directly.

Three Steps to Use Context

Using Context always involves three steps:

1. Create — define the context with createContext<T>(defaultValue)

2. Provide — wrap a subtree with <Context.Provider value={...}>

3. Consume — call useContext(Context) in any child component

Basic Example

Let's solve the props drilling problem from above using Context — same User, same components, but no forwarding:

Step 1: Create the context

// context/UserContext.ts
import { createContext } from "react";

type User = { name: string; avatarUrl: string };

export const UserContext = createContext<User | null>(null);

Step 2: Provide the value

// App.tsx
import { useState } from "react";
import { UserContext } from "./context/UserContext";

const App = () => {
  const [user] = useState({ name: "Alice", avatarUrl: "/alice.png" });

  return (
    <UserContext.Provider value={user}>
      <Layout />
    </UserContext.Provider>
  );
};

Step 3: Consume the value (in any nested component — no props needed!)

// Layout and Sidebar — no user prop, no forwarding!
const Layout = () => {
  return <Sidebar />;
};

const Sidebar = () => {
  return <UserMenu />;
};

// UserMenu and Avatar — read user directly from context
import { useContext } from "react";
import { UserContext } from "../context/UserContext";

const UserMenu = () => {
  const user = useContext(UserContext);
  return (
    <div>
      <span>{user?.name}</span>
      <Avatar />
    </div>
  );
};

const Avatar = () => {
  const user = useContext(UserContext);
  return <img src={user?.avatarUrl} alt={user?.name} />;
};

Compare with the drilling example above: Layout and Sidebar no longer accept or forward the user prop. UserMenu and Avatar read it directly from context — no matter how deeply nested they are.

TypeScript Typing

The generic parameter of createContext<T> defines the type of the value:

Simple value:

const LocaleContext = createContext<string>("");

Object value:

type AuthContextValue = {
  user: User;
  logout: () => void;
};

const AuthContext = createContext<AuthContextValue>({
  user: { id: "", name: "" },
  logout: () => {},
});

When there's no sensible default (context MUST be inside a Provider):

const AuthContext = createContext<AuthContextValue | undefined>(undefined);

Then in the consumer, you need to check for undefined — or better yet, use a custom hook that does it for you (covered in the next topic).

About the Default Value

The value you pass to createContext(defaultValue) is a fallback — it's only used if a component tries to read the context but there's no Provider above it. In practice, you always have a Provider, so the default rarely matters. Think of it as a safety net, not the actual data.
