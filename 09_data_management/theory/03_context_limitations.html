Context Is Powerful — But Has Limits

Context is a great tool for sharing data across the component tree. However, it has important limitations that you need to understand to choose the right tool for each situation.

Limitation 1: All Consumers Re-render When Value Changes

When the Provider's value changes, every component that calls useContext(ThatContext) re-renders — even if the component only uses one field from the context object.

// If AuthContext has { user, theme, locale } and only locale changes —
// ALL consumers re-render, even those that only read "user".

type AppContextValue = {
  user: User;
  theme: Theme;
  locale: string;
};

// This component re-renders when locale changes, even though it only uses "user":
const UserAvatar = () => {
  const { user } = useAppContext(); // re-renders on ANY context change
  return <img src={user.avatar} alt={user.name} />;
};

This is why splitting into multiple smaller contexts (one for auth, one for theme, one for locale) is important.

Limitation 2: No Built-in Selector

Unlike Redux (where you can select a specific slice of state), Context gives you the whole value. You can't say "only re-render me when user.name changes." You always get the entire context object, and any change to any part of it triggers a re-render.

Limitation 3: Provider Nesting Can Get Deep

With many contexts, you end up with "Provider hell":

<AuthProvider>
  <ThemeProvider>
    <LocaleProvider>
      <NotificationProvider>
        <FeatureFlagProvider>
          <App />
        </FeatureFlagProvider>
      </NotificationProvider>
    </LocaleProvider>
  </ThemeProvider>
</AuthProvider>

This is not a performance problem, but it hurts readability. You can mitigate it by composing providers into a single wrapper component.

When Context Is the Right Choice

Context works well for:

• Data that changes infrequently: theme, locale, auth status, feature flags

• Data needed by many components at different levels of the tree

• Simple state that doesn't require complex update logic

When Context Is NOT Enough

Context is not the right tool when:

• Data changes frequently (typing, scrolling, real-time updates) — causes too many re-renders

• Complex state with many actions (add/remove/update/filter) — gets messy in a Provider

• You need selectors (subscribe to specific parts of state without re-rendering on unrelated changes)

• You need middleware (logging, persistence, async handling)

What to Use Instead

For the cases where Context falls short, dedicated state management libraries exist:

• Redux Toolkit (covered in a later module) — provides selectors, middleware, DevTools, and predictable state updates for complex global state.

• Zustand (covered in a later module) — minimal API, built-in selectors, no Provider needed. Great for simpler global state without boilerplate.

These libraries are designed specifically for the performance and complexity challenges that Context can't handle well.
