The Real-World Pattern

In real projects, you never use raw createContext + useContext directly in components. Instead, you create a custom Provider component and a custom hook. This encapsulates the implementation details and provides a clean API.

The Pattern (4 Steps)

1. Create context (with undefined default)

2. Create a Provider component that holds state

3. Create a custom hook that consumes the context (with error handling)

4. Export only the Provider and the hook — hide the raw context

Full Example: ThemeContext with Toggle

// context/ThemeContext.tsx
import { createContext, useContext, useState, ReactNode } from "react";

type Theme = "light" | "dark";

type ThemeContextValue = {
  theme: Theme;
  toggleTheme: () => void;
};

const ThemeContext = createContext<ThemeContextValue | undefined>(undefined);

// Custom hook — safe access with error if used outside Provider
export const useTheme = (): ThemeContextValue => {
  const context = useContext(ThemeContext);
  if (!context) {
    throw new Error("useTheme must be used within a ThemeProvider");
  }
  return context;
};

// Custom Provider — encapsulates state logic
export const ThemeProvider = ({ children }: { children: ReactNode }) => {
  const [theme, setTheme] = useState<Theme>("light");

  const toggleTheme = () => {
    setTheme(prev => (prev === "light" ? "dark" : "light"));
  };

  return (
    <ThemeContext.Provider value={{ theme, toggleTheme }}>
      {children}
    </ThemeContext.Provider>
  );
};

Using the Provider in App:

// App.tsx
import { ThemeProvider } from "./context/ThemeContext";

const App = () => (
  <ThemeProvider>
    <Layout />
  </ThemeProvider>
);

Consuming in any component — clean, no imports of raw context:

// Any component
import { useTheme } from "../context/ThemeContext";

const ThemeToggle = () => {
  const { theme, toggleTheme } = useTheme();
  return (
    <button onClick={toggleTheme}>
      Current: {theme}. Click to switch.
    </button>
  );
};

Why This Pattern Is Better

1. Clean consumer API — the consumer doesn't need to know about the raw Context object, just the hook.

2. Error handling — if someone uses useTheme() outside of <ThemeProvider>, they get a clear error message instead of silent undefined.

3. Encapsulated state logic — all the useState, handlers, and side effects live inside the Provider component.

4. Easy to test — in tests, you can wrap components with a mock Provider that provides controlled values.

Another Example: AuthContext

The same pattern applies to any domain. Here's the type for an auth context:

type User = { id: string; name: string; email: string };

type AuthContextValue = {
  user: User | null;
  isAuthenticated: boolean;
  login: (email: string, password: string) => Promise<void>;
  logout: () => void;
};

// Same pattern applies:
// 1. createContext<AuthContextValue | undefined>(undefined)
// 2. AuthProvider component with useState, login/logout logic
// 3. useAuth() custom hook with undefined check
// 4. Export only AuthProvider and useAuth

Multiple Contexts

You can (and should) have separate contexts for separate concerns:

const App = () => (
  <AuthProvider>
    <ThemeProvider>
      <Layout />
    </ThemeProvider>
  </AuthProvider>
);

Each context is independent — changing the theme doesn't re-render components that only consume auth, and vice versa. This separation of concerns keeps your app performant and your code organized.
