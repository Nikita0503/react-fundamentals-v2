What Are Environments?

In real projects, your app runs in different environments — separate copies of the application for different purposes:

  • Development (your laptop) — where you write and test code locally. Uses a local or mock API.
  • Staging / QA — a server where the team tests new features before releasing to users. Uses a test database.
  • Production — the live app that real users see. Uses the real API and real data.

Each environment needs different settings: a different API URL, different analytics keys, different feature flags. You don't want to change code every time you deploy — you want the same code to behave differently depending on where it runs. That's what environment variables are for.

What Are Environment Variables?

Environment variables are configuration values that change between environments without changing code. Examples: API URL, feature flags, analytics keys.

They let you deploy the same codebase to different environments with different behavior — without editing a single line of source code.

Why Not Hardcode?

// ❌ Hardcoded — breaks when you deploy to production
const API_URL = "http://localhost:3001/api";

// ✅ Environment variable — different value per environment
const API_URL = import.meta.env.VITE_API_URL;

How It Works in Vite

You create separate .env files in your project root — one per environment. Vite automatically picks the right one based on how you run the app.

File: .env.development — used when you run npm run dev

VITE_API_URL=http://localhost:3001/api
VITE_APP_NAME=MyApp (Dev)

File: .env.production — used when you run npm run build

VITE_API_URL=https://api.myapp.com
VITE_APP_NAME=MyApp

How does Vite know which file to use?

  • npm run dev starts Vite in development mode → Vite reads .env.development
  • npm run build builds the app in production mode → Vite reads .env.production

You don't choose manually — Vite picks the file automatically based on the command you run. The values get "baked into" the JavaScript during build, replacing every import.meta.env.VITE_* with the actual string.

Custom Environments (e.g., Staging)

What if you have more than just dev and production? For example, a staging environment for QA testing. You can create custom modes:

1. Create the file: .env.staging

VITE_API_URL=https://staging-api.myapp.com
VITE_APP_NAME=MyApp (Staging)

2. Add scripts to package.json:

{
  "scripts": {
    "dev": "vite",                          // run app locally with .env.development
    "dev:staging": "vite --mode staging",   // run app locally with .env.staging (e.g., to test against staging API)
    "build": "vite build",                  // build for production with .env.production
    "build:staging": "vite build --mode staging"  // build for staging with .env.staging
  }
}

The --mode staging flag tells Vite: "use .env.staging instead of the default". Works for both vite (dev server) and vite build. You can create any mode you want — just match the file name to the mode name.

Using in your code:

// Access the variable
const apiUrl = import.meta.env.VITE_API_URL;

// Good practice: check that it exists (in case someone forgot to set it)
if (!import.meta.env.VITE_API_URL) {
  throw new Error("VITE_API_URL is not defined. Check your .env file.");
}

// Use it
const response = await fetch(`${import.meta.env.VITE_API_URL}/users`);

When you run npm run dev → import.meta.env.VITE_API_URL is "http://localhost:3001/api".
When you run npm run build → it becomes "https://api.myapp.com".
Same code, different values — no manual changes needed.

Where .env Files Live

Place .env files in the root of your project (next to package.json):

my-app/
├── .env.development      // used during npm run dev
├── .env.production       // used during npm run build
├── .env.local            // your personal overrides (gitignored!)
├── package.json
├── vite.config.ts
└── src/

Vite automatically finds and loads the right file based on the current mode. You don't need to import or configure anything — just create the file and it works.

What about Git?

  • .env.development and .env.production with non-secret defaults (like app name) — can be committed to Git so the whole team has them
  • .env.local with real values (API keys, tokens) — must be in .gitignore, never committed

When you join a new project and need the real values, you typically:

  • Ask a team lead or another developer
  • Check the team's password manager (1Password, Bitwarden, etc.)
  • Look in the project's CI/CD settings (GitHub Secrets, Vercel Environment Variables)
  • Check the project README — it often lists which variables are needed

VITE_ prefix is required — without it, the variable is NOT exposed to client code. This is a security measure: it prevents accidentally leaking server-side secrets to the browser.

Runtime vs Build-Time

  • Environment variables in Vite are build-time — they're replaced with actual values during npm run build
  • After build, you can't change them without rebuilding
  • This is different from server-side env vars (which can change at runtime without redeployment)

TypeScript Typing for Env Vars

By default, TypeScript doesn't know what environment variables exist. You can add type definitions so you get autocomplete and type checking:

// src/env.d.ts
/// <reference types="vite/client" />

interface ImportMetaEnv {
  readonly VITE_API_URL: string;
  readonly VITE_APP_NAME: string;
  readonly VITE_FEATURE_DARK_MODE: string;
}

interface ImportMeta {
  readonly env: ImportMetaEnv;
}

This gives you autocomplete and type checking for env vars — no more typos in variable names.

Security Rules

✅ OK to put in frontend env:

  • API URLs
  • Public keys (Stripe publishable key)
  • Feature flags
  • App name / version

❌ NEVER put in frontend env:

  • Secret keys
  • Database passwords
  • API secrets
  • Private tokens

Why: frontend code is visible to anyone (View Source, DevTools). Environment variables in the browser are NOT secret — they're baked into the JavaScript bundle. Anyone can open DevTools and see them.

Secret operations (payment processing, auth token generation) must happen on the backend.

# .gitignore
.env.local
.env.*.local
  • .env (with defaults) can be committed — it has no secrets
  • .env.local (with real values) should be gitignored
  • Share real values via team password manager or CI/CD secrets
