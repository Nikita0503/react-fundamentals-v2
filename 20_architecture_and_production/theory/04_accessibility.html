What Is Accessibility (a11y)

Accessibility (abbreviated "a11y" — "a", 11 letters, "y") means making your app usable by everyone, including people with disabilities — visual, motor, cognitive, and hearing impairments.

Why It Matters

  • 15%+ of the world's population has some form of disability
  • Legal requirements in many countries (ADA in US, EAA in EU)
  • Better SEO (search engines read semantic HTML the same way screen readers do)
  • Better UX for everyone (keyboard users, slow connections, small screens)

Semantic HTML — The Foundation

Semantic HTML means using elements that describe their purpose, not just their appearance. Screen readers (software that reads the page aloud for blind users) rely on semantic elements to understand page structure:

// ❌ Div soup — screen readers can't understand this
<div onClick={handleClick}>Click me</div>
<div className="heading">Page Title</div>

// ✅ Semantic — screen readers understand structure and purpose
<button onClick={handleClick}>Click me</button>
<h1>Page Title</h1>

Use the right element for the job:

  • <button> for actions
  • <a> for navigation
  • <h1>-<h6> for headings
  • <nav> for navigation sections
  • <main> for main content
  • <form> for forms

Rule: if it does something on click → <button>. If it goes somewhere → <a>. Never <div onClick>.

Heading Hierarchy

// ✅ Correct — logical hierarchy
<h1>Page Title</h1>
  <h2>Section</h2>
    <h3>Subsection</h3>
  <h2>Another Section</h2>

// ❌ Wrong — skipping levels
<h1>Title</h1>
  <h4>Subsection</h4>  // skipped h2 and h3!

Screen readers use headings to build a page outline. Skipping levels breaks that outline and confuses users who navigate by headings.

ARIA Basics

ARIA (Accessible Rich Internet Applications) is a set of HTML attributes that provide extra information to screen readers when semantic HTML alone isn't enough:

  • aria-label — provides a label when visible text isn't enough: 
    <button aria-label="Close dialog" onClick={onClose}>✕</button>
  • aria-hidden="true" — hides decorative elements from screen readers: 
    <span aria-hidden="true">🎉</span> Congratulations!
  • role — when you can't use semantic HTML (rare): 
    <div role="alert">Error: Invalid email</div>

Rule: prefer semantic HTML over ARIA. ARIA is a last resort when HTML doesn't have the right element. The first rule of ARIA is: don't use ARIA if you can use a native HTML element instead.

Keyboard Navigation

  • All interactive elements must be reachable via Tab key
  • <button> and <a> are focusable by default. <div> is not.
  • Focus order should follow visual order (don't use tabIndex > 0)
  • Focus trap in modals — Tab should cycle within the modal, not escape to background content. This prevents users from accidentally interacting with content behind the modal.
  • Visible focus indicator — never remove outline without providing an alternative:
/* ❌ Never do this */
*:focus { outline: none; }

/* ✅ Custom focus style */
button:focus-visible { outline: 2px solid blue; }

:focus-visible only shows the outline for keyboard users, not mouse clicks — best of both worlds.

Color Contrast

  • Text must have sufficient contrast against its background
  • WCAG AA standard: 4.5:1 ratio for normal text, 3:1 for large text (18px+ bold or 24px+ regular)
  • Don't rely on color alone to convey information — add icons, text, or patterns (colorblind users can't distinguish red from green)

Developer Checklist

  1. Can you use the entire app with only a keyboard? (no mouse)
  2. Does every interactive element have a visible focus state?
  3. Do all images have alt text (or aria-hidden if decorative)?
  4. Is the heading hierarchy logical (h1 → h2 → h3)?
  5. Do form inputs have associated labels?
  6. Are error messages announced to screen readers?
  7. Does color contrast meet WCAG AA (4.5:1)?
