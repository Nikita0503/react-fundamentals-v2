Why Structure Matters

A 5-file project doesn't need architecture. A 500-file project without structure is unmaintainable. Good structure means: easy to find code, easy to add features, easy to onboard new developers.

Structure is not about "the right way" — it's about consistency and scalability. Pick a pattern and stick with it across the team.

Two Main Approaches

Layer-Based (by type)

src/
├── components/     // ALL components
├── hooks/          // ALL hooks
├── utils/          // ALL utilities
├── types/          // ALL types
├── services/       // ALL API calls
└── pages/          // ALL pages
  • Pros: simple, clear where to put things — every file type has one home
  • Cons: at scale, folders become huge (50+ components in one folder). Related files are far apart — UserCard component, useUser hook, userApi service all live in different folders

Feature-Based (by domain)

src/
├── features/
│   ├── auth/
│   │   ├── components/
│   │   ├── hooks/
│   │   ├── api/
│   │   ├── types.ts
│   │   └── index.ts
│   ├── products/
│   │   ├── components/
│   │   ├── hooks/
│   │   ├── api/
│   │   ├── types.ts
│   │   └── index.ts
│   └── cart/
│       └── ...
├── components/     // shared/reusable components (Button, Modal, Input)
├── hooks/          // shared hooks (useDebounce, useLocalStorage)
├── utils/          // shared utilities
├── lib/            // third-party config (axios instance, query client)
└── pages/          // route-level page components
  • Pros: related code lives together, easy to find everything about a feature, features are independent (can delete a feature folder without breaking others)
  • Cons: more upfront decisions, shared vs feature-specific can be ambiguous

Practical Recommendation

  • Small project (<20 components): layer-based is fine
  • Medium/large project (20+ components): feature-based scales better
  • Most real-world projects use a hybrid: feature folders + shared folder for reusable pieces

Barrel Exports (index.ts)

A barrel export is a file that re-exports the public API of a folder — it acts as a single entry point so consumers don't need to know the internal file structure:

// features/auth/index.ts
export { LoginForm } from "./components/LoginForm";
export { useAuth } from "./hooks/useAuth";
export type { User, AuthState } from "./types";
  • Pros: clean imports (from "@/features/auth" instead of deep paths)
  • Cons: can cause circular dependencies, can slow down bundling if barrel re-exports everything
  • Rule: use barrels for the public API of a feature. Don't barrel internal implementation files.

Path Aliases (Absolute Imports)

Path aliases let you use short, absolute-style imports instead of long relative paths with ../../../:

// tsconfig.json
{
  "compilerOptions": {
    "paths": {
      "@/*": ["./src/*"]
    }
  }
}

// vite.config.ts
resolve: {
  alias: {
    "@": path.resolve(__dirname, "./src")
  }
}

// Usage:
import { Button } from "@/components/Button";  // instead of "../../../components/Button"

Always use absolute imports in projects with more than 2 levels of nesting.
