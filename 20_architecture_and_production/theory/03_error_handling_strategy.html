The Goal

Users see helpful messages, developers get debugging info, the app doesn't crash entirely. A good error handling strategy has multiple layers — each one catches what the previous one missed.

Multi-Level Error Handling Strategy

Level 1 — Global Error Boundary (app-level)

// Catches any unhandled rendering error in the entire app
<ErrorBoundary fallback={<FullPageError />}>
  <App />
</ErrorBoundary>
  • Last resort — catches anything that slipped through all other layers
  • Shows a "something went wrong, refresh" page
  • Remember from the Advanced React module: Error Boundaries are class components that use getDerivedStateFromError

Level 2 — Route-Level Error Boundaries

<Route path="/dashboard" element={
  <ErrorBoundary fallback={<p>Dashboard failed to load</p>}>
    <Dashboard />
  </ErrorBoundary>
} />
  • One page crashes → other pages still work
  • User can navigate away without refreshing the entire app

Level 3 — API Error Handling (TanStack Query / Axios interceptors)

// Global handler for all API errors
const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      retry: 2,
    },
    mutations: {
      onError: (error) => {
        logger.error("Mutation failed", { error });
        toast.error("Something went wrong. Please try again.");
      },
    },
  },
});
  • Handles: network errors, 4xx/5xx responses, timeouts
  • Shows toast notifications for recoverable errors

Level 4 — Component-Level try/catch (event handlers)

const handleSubmit = async (data: FormData) => {
  try {
    await submitForm(data);
    toast.success("Saved!");
  } catch (error) {
    if (error instanceof ValidationError) {
      setFieldErrors(error.fields);
    } else {
      toast.error("Failed to save. Please try again.");
      logger.error("Form submission failed", { error, data });
    }
  }
};
  • For specific user actions where you need custom error handling
  • Note: Error Boundaries don't catch errors in event handlers — only in render. That's why we need try/catch here.

Graceful Degradation

When part of the app fails, the rest should keep working. Don't let a broken sidebar kill the entire page. Each independent section should have its own error boundary so failures are isolated.

Logging Strategy

In production, you can't open DevTools on the user's browser. Logs are your only window into what happened when something goes wrong.

Log Levels

Logger Utility Pattern

// lib/logger.ts
type LogContext = Record<string, unknown>;

const isProd = import.meta.env.PROD;

export const logger = {
  error: (message: string, context?: LogContext) => {
    if (isProd) {
      // Send to error tracking service (Sentry, Datadog)
      // errorTracker.captureException(message, context);
    }
    console.error(`[ERROR] ${message}`, context);
  },

  warn: (message: string, context?: LogContext) => {
    if (isProd) {
      // Send to monitoring
    }
    console.warn(`[WARN] ${message}`, context);
  },

  info: (message: string, context?: LogContext) => {
    console.info(`[INFO] ${message}`, context);
  },

  debug: (message: string, context?: LogContext) => {
    if (!isProd) {
      console.debug(`[DEBUG] ${message}`, context);
    }
  },
};

Usage example:

import { logger } from "../lib/logger";

const UserProfile = ({ userId }: { userId: string }) => {
  const [user, setUser] = useState<User | null>(null);

  useEffect(() => {
    fetch(`/api/users/${userId}`)
      .then((res) => res.json())
      .then((data) => {
        setUser(data);
        logger.info("User loaded", { userId, name: data.name });
      })
      .catch((err) => {
        logger.error("Failed to load user", { userId, error: err.message });
      });
  }, [userId]);

  return user ? <p>{user.name}</p> : <p>Loading...</p>;
};

What to Log

  • ✅ API errors (status, URL, method, response time)
  • ✅ Unhandled exceptions (error message, component stack)
  • ✅ Critical user actions (login, logout, purchase)
  • ✅ Performance issues (slow renders, long API calls)

What NOT to Log

  • ❌ Personal data (names, emails, addresses, phone numbers)
  • ❌ Authentication tokens or passwords
  • ❌ Full request/response bodies with sensitive data
  • ❌ Every state change or re-render (too noisy)

console.log in Production — Antipattern

  • Clutters the browser console
  • Can accidentally expose sensitive information
  • Not structured (can't search/filter/alert on it)
  • Replace with the logger utility — it's the same effort to write but infinitely more useful

Error Tracking Services

  • Sentry — most popular, captures errors with full stack trace + user context
  • Datadog — monitoring + logging + APM in one platform
  • LogRocket — session replay + error tracking (see exactly what user did before the error)
  • These integrate with your logger utility — in production, logger.error() sends to the service automatically
