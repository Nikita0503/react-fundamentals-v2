Підсумки

В цьому модулі було розглянуто базове використання Redux, де є 1 Reducer та 2 Actions. При збільшенні коду додатку, кількість Reducers та Actions може збільшуватися.

Виникають питання:

"Як зрозуміти коли потрібно створювати нові Reducers?".

Відповідь - чіткого правила не існує, але можна користуватися принципом «Одна сторінка - один Reducer». Якщо додати до нашого прикладу сторінку зі списком задач та з формою логіну, цілком доцільно буде створити tasksReducer та loginReducer, тоді RootReducer буде приблизно виглядати так:

/** /redux/store */

import { combineReducers, createStore } from 'redux';
import userReducer from './reducers/userReducer';
import userReducer from './reducers/tasksReducer';
import userReducer from './reducers/loginReducer';

const rootReducer = combineReducers({
    user: userReducer,
    tasks: tasksReducer,
    login: loginReducer,
});

export const store = createStore(rootReducer);

"Чи потрібно переносити взагалі усі дані до Store?".

Відповідь - ні, не потрібно. Якщо існують якісь реактивні змінні, котрі впливають тільки на компонент, в котрому вони створюються та використовуються, та вони не потрібні у ішних містах коду, виносити їх у Store не має сенсу. Дані винесені у Store - це ті дані, котрі можуть бути використані у декільнох ділянах коду розташованих у різних частинах проекту.

"Чи не занадтно багато коду для роботи з Redux?".

Відповідь - насправді, boilerplate коду у Redux багато. І це є його найбільшим мінусом, але існує рішення - redux toolkit, який дозволяє писати менше коду.

"Чому ми одразу не розглядаємо redux toolkit для роботи з Redux?".

Відповідь - тому що для кращого розуміння технології краще розглядати Redux у чистому виді. Redux без toolkit може попадатися у проектах і краще розуміти як з ним працювати одразу, а потім toolkit можна розглянути самостійно. Так робити набагато легше ніж навпаки.

"Існують набагато простіші аналоги Redux, наприклад MobX, чому Redux?".

Відповідь - тому що його легше масштабувати, в нього більша популярність, а це свідчить про більшу довіру, через зручність, передбачуваність та стабілність. Більшість проектів використовують Redux.

"Це все? Чи в Redux є ще щось?".

Відповідь - є ще багато чого. Наприклад, redux-persist - вміє зберігати значення у Reducers, коли додаток зачиняється та відновити ці дані самостійно, після повторного відкриття. Redux-thunk / redux-saga - допоможе винести логіку взаємодії, наприклад з REST API, з компоненту в інші частини проекту для поліпшення архітектури та читабельності коду. Reselect - аналог useMemo з React, але для Redux. Цей список дуже великий. Через велику популярність, існує багато допоміжних бібліотек, котрі покривають майже 100% потреб.
