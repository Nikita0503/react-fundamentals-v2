Why do we need global state management?

As your React application grows, you'll face a common challenge: how do you share data between components that are far apart in the tree?

Consider a typical app: a header shows the user's name, a sidebar shows their avatar, and a settings page lets them update their profile. All these components need access to the same user data, but they live in completely different parts of the component tree.

The Prop Drilling Problem

The naive solution is to pass data down through props at every level:

// App → Layout → Header → UserMenu → Avatar
// Every intermediate component must accept and forward the prop

const Layout = ({ user }: { user: User }) => (
  <div>
    <Header user={user} />
    <Sidebar user={user} />
    <Main user={user} />
  </div>
);

const Header = ({ user }: { user: User }) => (
  <nav>
    <UserMenu user={user} />  {/* Header doesn't use user, just passes it */}
  </nav>
);

This is called prop drilling. It makes code harder to maintain, creates unnecessary coupling between components, and causes re-renders in components that don't even use the data.

When is useState enough?

Local UI state — things that only one component (or its direct children) cares about:

  • Is a modal open or closed?
  • What's the current input value?
  • Is a dropdown expanded?
  • Which tab is active?

If the state doesn't need to be shared — useState is perfect. Keep it simple.

When is Context enough?

Low-frequency, app-wide values that rarely change:

  • Current theme (light/dark)
  • Locale / language
  • Authentication status (logged in or not)

Context is great for these because they update infrequently. But Context has a limitation: every consumer re-renders when the value changes, even if they only use a small part of it.

When do you need Redux / Redux Toolkit?

You benefit from a dedicated state manager when:

  • Complex shared state — multiple components read and write the same data
  • Frequent updates — state changes often (e.g., form data, filters, lists)
  • Many consumers — dozens of components subscribe to the same slice of state
  • Predictability — you need a clear, traceable history of what changed and why
  • Debugging — Redux DevTools let you time-travel through state changes

The Core Idea: State Lives Outside Components

With useState, data lives inside a component — when the component unmounts, the data is gone. With Redux, data lives in a centralized store that exists outside the React component tree.

Components don't own the data. They just:

  • Read from the store (via selectors) — "show me the current user"
  • Request changes to the store (via dispatch) — "update the user's name"

This separation means:

  • Any component can access any data — no matter where it is in the tree
  • Data persists even if the component that created it unmounts
  • Multiple components can read the same data without passing props
  • All state changes go through one predictable path (dispatch → reducer → new state)

The Redux Data Flow

Redux follows a unidirectional data flow. Here's the mental model:

// The cycle:
// Component → dispatch(action) → reducer → new state → Component re-renders

// 1. Something happens in the UI (user clicks a button)
// 2. Component dispatches an action: { type: "user/setName", payload: "Alice" }
// 3. The reducer receives current state + action, returns NEW state
// 4. The store updates, and subscribed components re-render with fresh data

This predictable cycle means you always know what changed, why it changed, and when it changed. No magic, no hidden mutations.

Redux Toolkit (RTK) — the modern way

In this module, we'll use Redux Toolkit (RTK) — the official, recommended way to write Redux. It eliminates boilerplate while keeping all the benefits of Redux's architecture.

Install it:

npm install @reduxjs/toolkit react-redux

That's it — one package gives you everything you need. No more installing redux, redux-thunk, immer, or reselect separately.
