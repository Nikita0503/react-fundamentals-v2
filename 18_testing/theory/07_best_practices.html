What TO Test

  • Conditional rendering — shows X when prop is Y, hides Z when state is W
  • User interactions — click button → something visible happens
  • Callback invocations — child component calls parent's handler with correct arguments
  • Form validation — shows error message when input is invalid, submits when valid
  • Loading/error/success states — component shows correct UI for each state
  • Data transformations — utility functions that convert data from one format to another
  • Edge cases — empty arrays, null values, boundary conditions (0, negative numbers, very long strings)

What NOT to Test

  • Implementation details — internal state variable names, how many times setState was called, which internal function was used. If the user can't tell the difference, the test shouldn't care.
  • Static markup without logic — a div with fixed text that never changes. No logic = nothing to break.
  • Third-party library internals — don't test that React Router navigates correctly. Test that YOUR code calls navigate("/dashboard") with the right path.
  • CSS classes — unless they depend on props/state (like className={isActive ? "active" : ""})
  • That a component "renders without crashing" — too vague, catches nothing meaningful. Test specific behavior instead.

Snapshot Tests — Why They're an Antipattern

A "snapshot test" captures the entire rendered HTML output of a component and saves it to a file. Next time the test runs, it compares the current output to the saved snapshot. If anything changed, the test fails.

Why this sounds good but is actually harmful:

  • They break on ANY change — even intentional ones (adding a CSS class, changing text)
  • Developers just run "update snapshots" without reviewing what changed → tests become meaningless rubber stamps
  • They don't tell you WHAT broke or WHY — just "something in the HTML is different"
  • They give false confidence — 100 snapshot tests passing means nothing if nobody reviews the snapshots
// ❌ Snapshot — breaks on any change, tells you nothing useful
it("matches snapshot", () => {
  const { container } = render(<Button label="Click" />);
  expect(container).toMatchSnapshot();
});

// ✅ Specific assertion — tells you exactly what matters
it("renders the label text", () => {
  render(<Button label="Click" />);
  expect(screen.getByRole("button")).toHaveTextContent("Click");
});

Test File Structure

Co-locate tests next to source files — don't put them in a separate __tests__ folder:

src/
├── components/
│   ├── Button.tsx
│   ├── Button.test.tsx    ← right next to it
│   ├── Card.tsx
│   └── Card.test.tsx
├── utils/
│   ├── formatPrice.ts
│   └── formatPrice.test.ts

Benefits:

  • Easy to find — test is always next to the code it tests
  • Easy to see what's tested — missing .test file = missing tests
  • Moves with the file during refactoring — no broken paths

Coverage

"Coverage" is a percentage showing how much of your source code is actually executed during tests. There are several types:

  • Line coverage — what percentage of code lines were executed
  • Branch coverage — what percentage of if/else paths were taken
  • Function coverage — what percentage of functions were called

Guidelines:

  • Target: 80%+ is a good goal for most projects
  • 100% is usually not worth the effort — diminishing returns on the last 20%
  • Coverage doesn't mean quality — you can have 100% coverage with bad tests that assert nothing meaningful
  • Use coverage as a guide: "what important paths am I missing?" — not as a goal in itself

Common Mistakes

  1. Testing implementation, not behavior — "state was set to X" vs "user sees X on screen." Always test what the user would observe.
  2. Over-mocking — mocking so much that you're not testing anything real. If everything is fake, what are you actually verifying?
  3. Flaky tests — a "flaky test" is one that sometimes passes and sometimes fails without any code change. Usually caused by timing issues, race conditions, or tests depending on each other. Fix with: waitFor, findBy, proper cleanup.
  4. Testing library internals — testing that React Router navigates or that Zustand updates its store. Test YOUR code's behavior, not the library's.
  5. Not cleaning up — forgetting afterEach cleanup means one test's state leaks into the next, causing mysterious failures.

The Golden Rule

Test your code the way a user would use it. If a user can't tell the difference between two implementations, the test shouldn't either. Focus on inputs (props, user actions) and outputs (what appears on screen, what callbacks are called) — not on internal mechanics.
