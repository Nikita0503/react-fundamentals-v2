What Is a Unit Test?

A unit test tests a single "unit" of code in isolation — a function, a utility, a pure computation. It answers the question: "does this one piece work correctly by itself?"

The AAA Pattern

Every well-structured test has three parts (AAA = Arrange, Act, Assert):

  • Arrange — set up the data and conditions needed for the test
  • Act — call the function or trigger the action you're testing
  • Assert — check that the result is what you expected
it("formats price with dollar sign", () => {
  // Arrange
  const price = 10.5;

  // Act
  const result = formatPrice(price);

  // Assert
  expect(result).toBe("$10.50");
});

describe and it

  • describe("groupName", () => { ... }) — groups related tests together under a common name
  • it("does something specific", () => { ... }) — defines one individual test case
  • Read them together as a sentence: "describe formatPrice → it formats price with dollar sign"

Common Matchers

Matchers are the methods that perform the actual comparison. Here are the ones you'll use most:

// Equality
expect(value).toBe(5);              // strict equality (===) — use for primitives (numbers, strings, booleans)
expect(obj).toEqual({ a: 1 });      // deep equality — use for objects and arrays (compares contents)

// Truthiness
expect(value).toBeTruthy();         // passes if value is not null/undefined/0/""
expect(value).toBeFalsy();          // passes if value IS null/undefined/0/""
expect(value).toBeNull();           // passes only if value === null
expect(value).toBeUndefined();      // passes only if value === undefined

// Numbers
expect(value).toBeGreaterThan(3);
expect(value).toBeLessThanOrEqual(10);

// Strings
expect(str).toContain("hello");     // checks if "hello" is a substring
expect(str).toMatch(/pattern/);     // checks against a regex pattern

// Arrays
expect(arr).toHaveLength(3);        // array has exactly 3 items
expect(arr).toContain("item");      // array includes "item" (works for primitives)

// For arrays of objects — use toContainEqual (deep comparison):
expect(users).toContainEqual({ id: 1, name: "Alice" }); // finds object with matching content

// Errors — testing that a function throws (e.g., invalid input should cause an error)
// Wrap in () => ... so expect can call the function itself and catch the throw
expect(() => riskyFn()).toThrow();                  // passes if function throws ANY error
expect(() => riskyFn()).toThrow("specific message"); // passes if error message contains this text

Full Example — Testing a Utility Module

// src/utils/formatDate.ts
export const formatDate = (date: Date): string => {
  return date.toLocaleDateString("en-US", {
    month: "short",
    day: "numeric",
    year: "numeric",
  });
};

export const isToday = (date: Date): boolean => {
  const today = new Date();
  return date.toDateString() === today.toDateString();
};
// src/utils/formatDate.test.ts
import { describe, it, expect } from "vitest";
import { formatDate, isToday } from "./formatDate";

describe("formatDate", () => {
  it("formats date in US format", () => {
    const date = new Date("2025-03-15");
    expect(formatDate(date)).toBe("Mar 15, 2025");
  });
});

describe("isToday", () => {
  it("returns true for today's date", () => {
    expect(isToday(new Date())).toBe(true);
  });

  it("returns false for yesterday", () => {
    const yesterday = new Date();
    yesterday.setDate(yesterday.getDate() - 1);
    expect(isToday(yesterday)).toBe(false);
  });
});

Test Naming Conventions

  • Describe WHAT the function does, not HOW it does it internally
  • Good: "returns empty array when input is empty"
  • Good: "throws error when email is invalid"
  • Bad: "test 1", "works correctly", "should work"
  • Think of test names as a specification — someone reading just the test names should understand what the function does
