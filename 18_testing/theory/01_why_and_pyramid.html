Why Test?

Before we dive into tools and syntax, let's understand WHY developers write automated tests:

  • Confidence — you know your code works without manually clicking through the app every time you make a change.
  • Regression prevention — a "regression" means something that used to work now breaks after a code change. Tests catch regressions automatically — you change one file, run tests, and instantly know if you broke something elsewhere.
  • Documentation — tests describe what the code is supposed to do. New developers read tests to understand expected behavior faster than reading implementation code.
  • Refactoring safety — "refactoring" means changing the internal structure of code without changing its behavior. With tests, you can refactor freely — if tests still pass, behavior is preserved.

The Testing Pyramid

The testing pyramid is a model that shows how many tests of each type you should have. Think of it as a triangle — wide at the bottom, narrow at the top:

LevelTypeHow many?SpeedConfidence
TopE2E (End-to-End)FEWSlowestHighest
MiddleIntegrationSOMEMediumHigh
BaseUnitMOSTFastestGood

Unit Tests (Base — MOST tests)

  • Test a single function, hook, or component in isolation
  • Fast (milliseconds), cheap to write, run often
  • Example: "does formatPrice(10.5) return '$10.50'?"
  • If it breaks, you know exactly WHERE the problem is

Integration Tests (Middle — SOME tests)

  • Test multiple units working together as a group
  • Example: "does the login form validate input, call the API, and redirect on success?"
  • Slower than unit tests, but more realistic — they catch bugs in how pieces connect

End-to-End (E2E) Tests (Top — FEW tests)

  • Test the entire app from the user's perspective — real browser, real clicks, real navigation
  • Tools: Playwright, Cypress
  • Slowest, most expensive to write and maintain, but highest confidence that the whole system works
  • Usually written by QA engineers or a dedicated team
  • We won't cover E2E in this course — just know they exist at the top of the pyramid

What a Frontend Developer Writes

As a frontend developer, you'll write mostly unit + integration tests. In React, the line between them is blurry — rendering a component with its children and mocking only the API is already an integration test. Don't worry about classifying perfectly — focus on testing behavior.

Key Terminology

These terms will appear throughout the course. Here's what each one means in plain language:

  • Test runner — the tool that finds your test files, executes them, and reports results. Examples: Vitest, Jest. Think of it as the "engine" that runs your tests.
  • Assertion — a statement in your test that checks if something is true. Example: expect(result).toBe(5) — this asserts that result equals 5. If it doesn't, the test fails.
  • Matcher — the method that does the actual comparison in an assertion. In expect(result).toBe(5), the matcher is .toBe(). Other matchers: .toEqual(), .toContain(), .toBeNull().
  • Mock — a fake version of something (a function, a module, an API) used to isolate what you're testing. Instead of calling a real API, you use a mock that returns predictable data instantly.
  • Coverage — a percentage showing how much of your source code is actually executed when tests run. 80% coverage means 80% of your code lines were hit during testing. It's a useful metric but not a guarantee of quality.
