Simulating User Interactions

Components are interactive — users click buttons, type in inputs, submit forms. Testing libraries provide two ways to simulate these interactions:

fireEvent — Simple and Fast

fireEvent dispatches a single DOM event synchronously. It's fast and straightforward:

// Counter.tsx — the component
import { useState } from "react";

const Counter = () => {
  const [count, setCount] = useState(0);
  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(count + 1)}>Increment</button>
    </div>
  );
};
// Counter.test.tsx — the test
import { render, screen, fireEvent } from "@testing-library/react";

it("increments counter on click", () => {
  render(<Counter />);
  fireEvent.click(screen.getByRole("button", { name: "Increment" }));
  expect(screen.getByText("Count: 1")).toBeInTheDocument();
});

userEvent — More Realistic

userEvent simulates the full event sequence that a real user triggers. For example, typing fires: focus → keydown → keypress → input → keyup for each character. This catches bugs that fireEvent misses (like form validation that triggers on blur):

// SearchBar.tsx
import { useState } from "react";

const SearchBar = () => {
  const [value, setValue] = useState("");
  return <input value={value} onChange={(e) => setValue(e.target.value)} placeholder="Search..." />;
};
// SearchBar.test.tsx
import userEvent from "@testing-library/user-event";

it("types in the search input", async () => {
  const user = userEvent.setup(); // creates a userEvent instance (required before using user.type, user.click, etc.)
  render(<SearchBar />);

  const input = screen.getByPlaceholderText("Search...");
  await user.type(input, "react");

  expect(input).toHaveValue("react");
});

When to Use Which?

  • fireEvent — simple clicks, fast tests, when you don't need the full event simulation
  • userEvent — typing, tabbing, complex interactions, when you need realistic behavior (form validation triggers, focus management, etc.)

Testing Forms

Forms combine multiple interactions. Here's a complete form test using userEvent:

// ContactForm.tsx
type ContactFormProps = {
  onSubmit: (data: { name: string; email: string }) => void;
};

const ContactForm = ({ onSubmit }: ContactFormProps) => {
  const [name, setName] = useState("");
  const [email, setEmail] = useState("");

  const handleSubmit = (e: React.FormEvent) => {
    e.preventDefault();
    onSubmit({ name, email });
  };

  return (
    <form onSubmit={handleSubmit}>
      <label>Name<input value={name} onChange={(e) => setName(e.target.value)} /></label>
      <label>Email<input value={email} onChange={(e) => setEmail(e.target.value)} /></label>
      <button type="submit">Submit</button>
    </form>
  );
};
// ContactForm.test.tsx
it("submits form with entered data", async () => {
  const handleSubmit = vi.fn(); // vi.fn() creates a mock function (a fake that tracks calls)
  const user = userEvent.setup(); // creates a userEvent instance (required before using user.type, user.click, etc.)
  render(<ContactForm onSubmit={handleSubmit} />);

  await user.type(screen.getByLabelText("Name"), "Alice");
  await user.type(screen.getByLabelText("Email"), "alice@test.com");
  await user.click(screen.getByRole("button", { name: "Submit" }));

  expect(handleSubmit).toHaveBeenCalledTimes(1);
  expect(handleSubmit).toHaveBeenCalledWith({
    name: "Alice",
    email: "alice@test.com",
  });
});

Testing Async Behavior (API Calls)

Many components fetch data from APIs. To test them, you mock the API call (replace it with a fake that returns predictable data), then wait for the UI to update:

// PostList.tsx — the component
import { useState, useEffect } from "react";

type Post = { id: number; title: string };

const PostList = () => {
  const [posts, setPosts] = useState<Post[]>([]);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    fetch("/api/posts")
      .then((res) => res.json())
      .then((data) => setPosts(data))
      .finally(() => setLoading(false));
  }, []);

  if (loading) return <p>Loading...</p>;
  return <ul>{posts.map((p) => <li key={p.id}>{p.title}</li>)}</ul>;
};
// PostList.test.tsx — the test
import { vi } from "vitest";

// Mock fetch globally — replace the real fetch with a fake
global.fetch = vi.fn();

it("displays posts after loading", async () => {
  // Arrange: tell the fake fetch what to return
  (fetch as ReturnType<typeof vi.fn>).mockResolvedValueOnce({
    ok: true,
    json: () => Promise.resolve([{ id: 1, title: "Test Post" }]),
  });

  render(<PostList />);

  // Initially shows loading state
  expect(screen.getByText("Loading...")).toBeInTheDocument();

  // Wait for data to appear (findBy waits automatically)
  expect(await screen.findByText("Test Post")).toBeInTheDocument();

  // Loading is gone
  expect(screen.queryByText("Loading...")).not.toBeInTheDocument();
});

waitFor — When findBy Isn't Enough

findBy waits for an element to appear. But what if you need to wait for something else — like an element to disappear, or a mock function to be called? That's where waitFor comes in. It repeatedly runs your assertion until it passes (or times out after 1 second).

import { render, screen, waitFor } from "@testing-library/react";

it("hides loading spinner after data loads", async () => {
  (fetch as ReturnType<typeof vi.fn>).mockResolvedValueOnce({
    ok: true,
    json: () => Promise.resolve([{ id: 1, title: "Post" }]),
  });

  render(<PostList />);

  // Loading is visible initially
  expect(screen.getByText("Loading...")).toBeInTheDocument();

  // Wait for loading to DISAPPEAR — can't use findBy for this (findBy finds elements, not their absence)
  await waitFor(() => {
    expect(screen.queryByText("Loading...")).not.toBeInTheDocument();
  });
});

When to use findBy vs waitFor:

  • findBy — waiting for an element to appear: await screen.findByText("Hello")
  • waitFor — waiting for anything else: element disappears, function was called, value changed

Test Lifecycle Hooks — beforeAll, beforeEach, afterEach, afterAll

These functions let you run code before or after your tests — for setup and cleanup:

beforeAll(() => {
  // Runs ONCE before all tests in this file start
  // Use for: one-time setup (start MSW mock server, set global config)
});

beforeEach(() => {
  // Runs before EACH individual test
  // Use for: resetting state, clearing mocks so tests don't affect each other
  vi.clearAllMocks();
});

afterEach(() => {
  // Runs after EACH individual test
  // Use for: cleanup (reset mock handlers, clear timers)
});

afterAll(() => {
  // Runs ONCE after all tests in this file finish
  // Use for: final cleanup (stop mock server, close connections)
});

Why they matter: without cleanup, one test can leave behind state that breaks the next test. beforeEach + afterEach ensure each test starts fresh and independent.

MSW (Mock Service Worker) — Realistic API Mocking

MSW is a more realistic way to mock APIs. Instead of replacing the fetch function directly, MSW intercepts network requests at the network level. Your component code runs exactly as in production — it calls real fetch, and MSW intercepts the request and returns mock data.

// mocks/handlers.ts
import { http, HttpResponse } from "msw";

export const handlers = [
  http.get("/api/posts", () => {
    return HttpResponse.json([
      { id: 1, title: "Mocked Post" },
    ]);
  }),
];
// mocks/server.ts
import { setupServer } from "msw/node";
import { handlers } from "./handlers";

export const server = setupServer(...handlers);
// test setup (in your setup file or test file)
beforeAll(() => server.listen());       // start intercepting requests
afterEach(() => server.resetHandlers()); // reset to default handlers between tests
afterAll(() => server.close());          // stop intercepting

Benefits of MSW:

  • No mocking fetch/axios directly — your component code is untouched
  • Tests are more realistic — the full request/response cycle runs
  • Handlers are reusable across many tests
  • Install: npm install -D msw
